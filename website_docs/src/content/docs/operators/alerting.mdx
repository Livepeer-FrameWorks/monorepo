vmalert evaluates the rules in `pkg/grafana/rules/` (`frameworks.yml` for platform services,
`infrastructure.yml` for hosts and data stores) and sends firing and resolved alerts to
Alertmanager. Alertmanager groups them by `alertname`, `region`, and `cluster` and routes
each group three ways:

- **Lookout** receives every group. Lookout (`api_incidents`) turns groups into incidents, keeps a
  timeline, notifies operator email, Slack, and Discord, and scopes incidents on tenant-owned
  clusters to that tenant.
- **Direct email** receives critical alerts as well, so a page still goes out if Lookout is down.
- **External heartbeat** receives only the always-firing `Watchdog` alert, once a minute. Configure
  your heartbeat provider to alarm when those pings stop; that detects a dead vmalert or
  Alertmanager.

Set `ALERTMANAGER_EXTERNAL_NOTIFICATIONS_ENABLED=false` for an internal-only staging environment.
Alertmanager continues sending actionable alerts to Lookout, while it discards `Watchdog` and does
not configure the heartbeat or direct-email receivers. Lookout's own email, Slack, and Discord
channels remain independently controlled by their optional destination variables.

Lookout notifies operator channels only for platform incidents. Critical incidents go to every
configured channel; other severities go to Slack and Discord. Notifications are sent when an
incident opens and when it resolves.

## Infrastructure coverage

`frameworks cluster provision` installs the exporters behind the infrastructure rules from the
release manifest's pinned artifacts. Each listens on loopback and is scraped by the vmagent on the
same host; nothing needs adding to the cluster manifest.

| Source                                                                | Where it runs                              | Port (loopback)              | Rules                                                                                                                                                                                      |
| --------------------------------------------------------------------- | ------------------------------------------ | ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| node_exporter with the systemd collector and the host crash scan      | every `vmagent` host and every native edge | 9110                         | filesystem space and inodes, disk I/O latency and saturation, iowait, memory and PSI pressure, OOM kills, load, clock sync, systemd restarts and failed units, process crashes             |
| JMX exporter in each Kafka broker and KRaft controller                | Kafka hosts                                | 9405 broker, 9406 controller | quorum leader, election churn, unreachable voters, active controller count, offline / under-min-ISR / under-replicated partitions, fenced brokers, controller event queue, metadata errors |
| YugabyteDB yb-master and yb-tserver `/prometheus-metrics`             | YugabyteDB nodes                           | 7000, 11000 (mesh)           | leaderless tables, follower lag                                                                                                                                                            |
| redis_exporter per Redis/Valkey server (Sentinels excluded)           | Redis hosts                                | instance port + 10000        | down, replica lost its primary, primary count per Sentinel set, failed background saves                                                                                                    |
| postgres_exporter per PostgreSQL instance (peer auth over the socket) | PostgreSQL hosts                           | instance port + 10000        | down, replica lag                                                                                                                                                                          |
| ClickHouse built-in Prometheus endpoint                               | ClickHouse hosts                           | 9363                         | read-only replicas, lost Keeper session, replication delay, part count, broken distributed inserts                                                                                         |

`ServiceDown` fires for any of these scrape targets that stops answering.

The host crash scan (`frameworks-host-crash-scan.timer`) runs every minute and counts the kernel's
fatal-signal reports (`segfault at`, general protection and trap faults) and `systemd-coredump`
dumps in the journal over the last fifteen minutes. It catches crashes of child processes, such
as Mist's `MistProc*` workers, that never fail a systemd unit. `HostProcessCrashed` names the
process; `journalctl -k` and `coredumpctl list` on the host hold the details.
`SystemdServiceRestarting` fires on any restart systemd makes under `Restart=`; operator and deploy
restarts do not count.

## Secrets

Set these in your gitops secrets. The CLI renders the Lookout webhook URL
(`http://lookout.internal:18022/v1/alertmanager`) from the manifest, so it is not a secret.

Every service receives the manifest's shared `env_files`, so each key below is set once, for
example in `secrets/production.env`; Alertmanager needs no env file of its own.

**Alertmanager:**

| Key                                    | Required | Purpose                                                         |
| -------------------------------------- | -------- | --------------------------------------------------------------- |
| `LOOKOUT_ALERTMANAGER_TOKEN`           | Yes      | Bearer token sent to Lookout; the same key Lookout reads        |
| `ALERTMANAGER_HEARTBEAT_URL`           | Yes      | Webhook URL of your external heartbeat monitor                  |
| `ALERTMANAGER_EMAIL_TO`                | Yes      | Recipient for the direct critical email fallback                |
| `SMTP_HOST`, `SMTP_PORT`, `FROM_EMAIL` | Yes      | Platform SMTP server and sender the fallback email is sent with |
| `SMTP_USER`, `SMTP_PASSWORD`           | No       | Platform SMTP credentials, used when set                        |

The heartbeat, direct-email recipient, and SMTP fields are required only when
`ALERTMANAGER_EXTERNAL_NOTIFICATIONS_ENABLED` is true (the default). The Lookout token is always
required.

The fallback sends through the platform SMTP settings. `ALERTMANAGER_SMTP_SMARTHOST`,
`ALERTMANAGER_SMTP_FROM`, `ALERTMANAGER_SMTP_AUTH_USERNAME`, `ALERTMANAGER_SMTP_AUTH_PASSWORD` and
`ALERTMANAGER_WEBHOOK_URL` are not read.

**Lookout:**

| Key                                                    | Required  | Purpose                                                                      |
| ------------------------------------------------------ | --------- | ---------------------------------------------------------------------------- |
| `LOOKOUT_ALERTMANAGER_TOKEN`                           | Yes       | Token Alertmanager must present; Lookout does not start without it           |
| `LOOKOUT_NOTIFY_EMAIL_TO`                              | No        | Comma-separated operator recipients; enables email notifications             |
| `LOOKOUT_SLACK_WEBHOOK_URL`                            | No        | Slack incoming webhook; enables incident and operator-activity notifications |
| `LOOKOUT_DISCORD_WEBHOOK_URL`                          | No        | Discord webhook; enables incident and operator-activity notifications        |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` | For email | Shared SMTP settings                                                         |
| `FROM_EMAIL`, `FROM_NAME`                              | No        | Sender address and display name                                              |
| `WEBAPP_PUBLIC_URL`                                    | No        | Adds an "Open incident" link to `/admin/incidents/<id>` in notifications     |

Each notification channel is active only while its key is set. Lookout re-reads these keys on
every use, so an env reload changes routing without a restart.

Use `LOOKOUT_OPS_SLACK_WEBHOOK_URL` / `LOOKOUT_OPS_DISCORD_WEBHOOK_URL` for incidents
and cluster subscription requests, and `LOOKOUT_BUSINESS_PULSE_SLACK_WEBHOOK_URL` /
`LOOKOUT_BUSINESS_PULSE_DISCORD_WEBHOOK_URL` for the other existing business activity.
Each destination uses an incoming webhook for its target channel; Slack can keep the
same app. Configure both purposes before setting `LOOKOUT_NOTIFY_LEGACY_FALLBACK=false`.
The per-purpose `*_NOTIFICATIONS_DISABLED` flags disable that purpose explicitly.
Email retains its existing critical-ops recipients; tenant in-app incidents and
investigations keep their existing routes. Livepeer/network notifications are disabled.

Upgrade all Lookout replicas before enabling these destinations. Queued delivery IDs
pin their purpose and target; old unclassified rows continue using the legacy webhook.
Keep the shared URLs until those rows drain, and drain purpose-routed rows before
downgrading to a binary that does not understand the destination IDs.
Slack and Discord also receive Lookout's fixed allowlist of direct signup,
product, billing, support, and marketing activity events. These activity
messages are separate from incidents and never page by email.

<Aside type="caution">
  A webhook URL is a credential. Lookout never writes it to logs or delivery errors; keep it in
  encrypted secrets only.
</Aside>

## Database

Lookout stores incidents in the `lookout` PostgreSQL/YugabyteDB database. Add it to
`postgres.databases` in the cluster manifest. On a new cluster `frameworks cluster provision`
creates it. On an existing cluster, `frameworks cluster release apply` (or
`frameworks cluster migrate --phase expand`) creates the missing database with its owner and
runtime roles and applies its baseline before Lookout deploys; `--dry-run` lists it without
creating anything. `frameworks cluster upgrade lookout` refuses until the database exists.

Delivered incident and activity rows are deleted after 7 days. A delivery that keeps failing is
abandoned after 20 attempts (about two hours), recorded as
`lookout_deliveries_total{result="failed"}` with its last error, and deleted after 30 days.
Activity selection and enqueue outcomes are recorded in
`lookout_operator_activity_events_total`.

## Verify

### Media authority access checks

`MediaAuthorityRevocationCheckFailed` is critical: Commodore could not finish an
access-change check after compilation failed, or could not publish the required
deny. A previous signed allow may remain usable until retry or expiry. Check
Commodore logs for `authority_id` and `stage`, then run
`frameworks cluster diagnose media-authority`. The stages distinguish reading the
previous authority, decoding it, reading playback or placement configuration, and
publishing the deny. No policy secrets are included in the metric labels.

The alert fires on a counter increase within ten minutes and clears when that
window contains no further failures. This is separate from
`MediaAuthorityRefreshParked`, which warns after a compile target has remained
parked for fifteen minutes. A missing dependency alone does not revoke unchanged
playback access.

### Placement membership

`FoghornPlacementMembershipUnconfirmed` warns when a Foghorn replica has not had its
placement membership (the cell's clusters and the admission state of their edge nodes)
confirmed by Quartermaster for two minutes. The replica keeps placing from the membership
it holds, which survives restarts, so viewers and publishers are not refused. Node drains,
cluster deactivations and control-cell moves made in Quartermaster since then do not reach
that cell until it is confirmed again. Check the replica's connection to Quartermaster;
`foghorn_placement_membership_snapshot_age_seconds` shows the age per replica.

### Notification delivery

1. **Heartbeat.** Confirm your heartbeat provider shows a ping roughly every minute from
   Alertmanager.
2. **Lookout ingestion.** From a host on the private network, send a test notification. Use a new
   `groupKey` and `fingerprint` for each test run:

   ```bash
   curl -sS -X POST http://lookout.internal:18022/v1/alertmanager \
     -H "Authorization: Bearer $LOOKOUT_ALERTMANAGER_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"version":"4","groupKey":"operator-test-1","status":"firing",
          "groupLabels":{"alertname":"OperatorTest"},
          "commonAnnotations":{"summary":"Lookout delivery test"},
          "alerts":[{"status":"firing","fingerprint":"operator-test-1",
                     "labels":{"alertname":"OperatorTest","severity":"critical"},
                     "startsAt":"2026-01-01T00:00:00Z"}]}'
   ```

   The response is `{"outcome":"created","incident_id":"..."}`. A `401` means the token does not
   match. Check the counter:

   ```bash
   curl -sS http://lookout.internal:18022/metrics | grep lookout_alertmanager_webhooks_total
   ```

3. **Notifications.** The test alert is critical, so every configured channel receives an
   "[CRITICAL] Lookout delivery test" message within a few seconds. Delivery failures show in
   `lookout_deliveries_total{result="error"}` and Lookout's logs; failed deliveries retry with
   backoff.
4. **Resolve the test.** Send the same request with both `status` fields set to `resolved` and an
   `endsAt`. The response outcome is `resolved` and the channels receive a "[RESOLVED]" message.
