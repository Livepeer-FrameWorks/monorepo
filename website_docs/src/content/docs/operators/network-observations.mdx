---
title: Livepeer network observations
description: Publish network inventory and real gateway performance with external discovery probers.
---

The public Livepeer tab at `/network?view=livepeer` and `GET /v1/network/livepeer` API combine Livepeer discovery
with real gateway transcoding observations. Unknown coverage remains unknown; regional
performance is shown separately. The platform-operator webapp can enable private
correlation through the authenticated diagnostics route.
The default FrameWorks tab shows infrastructure topology. Livepeer has Compare and Map
modes with shared filters and independent worker, gateway-cluster and prober layers.
Gateway map positions are cluster locations. Unknown prober/worker locations remain
listed. Price and performance comparisons retain their units, region and profile.

This feature requires platform `v0.3.13` and CLI `v0.3.13` or later. Upgrade
existing clusters with the release's ClickHouse expand migration and initialize
the new observer database from its baseline.

## Coordinator

Declare `network-observer` under the cluster manifest's `services`, with an enabled
entry, a host in the aggregator region, and that host's platform cluster ID. Both
`native` and `docker` modes are supported by the CLI. It is an opt-in service, also
available in the `network-observations` selection profile; the default profiles do
not start an observer. External probers are not part of that profile or CLI enrollment.

Add the `network_observer` database to the selected managed SQL deployment's database
list. The release bootstrap creates its baseline and `network_observer_runtime` role
before deploying the observer. The CLI derives its database connection from this
declaration and the existing database credentials. For a manually managed service,
build with `make build-bin-network-observer` and apply the same baseline to its own
database using the normal database tooling.

For the new database, set `owner: network_observer` and
`runtime_role: network_observer_runtime`. Supply the runtime password through the
existing `DATABASE_RUNTIME_PASSWORD` secret, or the database-specific
`POSTGRES_NETWORK_OBSERVER_RUNTIME_PASSWORD`; the latter takes precedence. Keep the
owner/bootstrap credential separate. An omitted `runtime_role` preserves an owner DSN
for compatibility; declaring it makes the observer connect with the runtime role.

Configure `DATABASE_URL`,
`NETWORK_OBSERVER_TENANT_ID`, `NETWORK_OBSERVER_CLUSTER_ID`, `NETWORK_OBSERVER_SECRET`,
`LIVEPEER_ETH_RPC_URL`, `LIVEPEER_CONTROLLER`, `DECKLOG_GRPC_ADDR`, `SERVICE_TOKEN` and
`KAFKA_BROKERS`. Use the production Arbitrum chain and choose the observation environment
explicitly. Configure verified internal gRPC TLS as for other services. The optional
`docker-compose.network-observations.yml` overlay is for isolated local use.

CLI provisioning defaults the observer tenant to the resolved system tenant and its
cluster to the manifest task's cluster; explicit observer values take precedence.
`LIVEPEER_ETH_RPC_URL` can use the existing `ARBITRUM_RPC_ENDPOINT` when not explicitly
set. The shared secret and controller address still require operator input. The CLI
generates the aggregator Kafka binding, `MIRROR_REGION_PREFIXES` from inbound
MirrorMaker links, and aggregator-region `DECKLOG_GRPC_ADDR`. Manual deployments must
set the source aliases themselves to include gateway discovery from other regions.

Expose the shared-secret work and ingest routes through verified HTTPS. If behind an
ingress, set `NETWORK_OBSERVER_TRUSTED_PROXY_CIDRS` to the actual ingress CIDRs before
using its forwarded source addresses for prober geolocation. Optional `GEOIP_MMDB_PATH`
provides coordinates; missing geography does not prevent discovery.

Use an explicit `ingress_sites` entry with `kind: reverse_proxy_http`, the chosen
`domains`, the proxy `node`/`cluster`, its existing `tls_bundle_id`, and an `upstream`
pointing to the observer's HTTP listener. The coordinator has no automatically selected
public hostname. A co-located proxy can use `127.0.0.1:18024`; another proxy uses the
observer's reachable mesh address. Configure the matching DNS and TLS bundle through
the existing ingress/control-plane lifecycle, then use that verified HTTPS URL for
Bridge and the external probers.

Bridge needs `NETWORK_OBSERVER_URL`, `NETWORK_OBSERVER_SECRET`,
`NETWORK_PUBLIC_TENANT_IDS` and the matching `NETWORK_OBSERVER_ENVIRONMENT`. Publication
scopes are server configuration, not caller-supplied query parameters. Periscope runs
the canonical migration and rollup loop as part of its existing ingestion service.

## GitOps inputs and activation order

The observer binary and prober binaries/images ship with the platform release;
gateways use the separately released compatible go-livepeer fork. The platform's
release manifest provides artifact pins, not host placement or configuration.
Complete these declarations before activating the feature:

| Location                          | Required inputs                                                                                                                                                                                                                                                 |
| --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Cluster manifest                  | Enabled observer service with aggregator-region host/cluster, `network_observer` database, HTTPS ingress for the coordinator, and optional GeoIP service selection/trusted proxy CIDRs.                                                                         |
| Observer service configuration    | `LIVEPEER_CONTROLLER`, `NETWORK_OBSERVER_ENVIRONMENT`; verify `LIVEPEER_NETWORK_ID=42161` and the resolved observer tenant/cluster.                                                                                                                             |
| SOPS-managed service environment  | `NETWORK_OBSERVER_SECRET` and `LIVEPEER_ETH_RPC_URL` (or the existing Arbitrum RPC key); preserve existing database credentials and internal `SERVICE_TOKEN`.                                                                                                   |
| Bridge configuration/environment  | Verified HTTPS `NETWORK_OBSERVER_URL`, matching secret and environment, and explicit `NETWORK_PUBLIC_TENANT_IDS` for the dataset to publish.                                                                                                                    |
| Gateway configuration/environment | Compatible fork artifact pin, stable gateway ID/region/cluster owner, verified Decklog connection and persistent telemetry spool; `FRAMEWORKS_NETWORK_ID=42161` and matching `FRAMEWORKS_ENVIRONMENT`. Candidate hints are optional and start in `shadow` mode. |
| Lookout service environment       | Optional `LOOKOUT_OPS_SLACK_WEBHOOK_URL`, `LOOKOUT_OPS_DISCORD_WEBHOOK_URL`, `LOOKOUT_BUSINESS_PULSE_SLACK_WEBHOOK_URL`, `LOOKOUT_BUSINESS_PULSE_DISCORD_WEBHOOK_URL` to split the existing destinations.                                                       |

Keep credentials in encrypted env files referenced by the services. Edit GitOps secrets
with `gitops/scripts/sops-env.sh`, not by editing encrypted content. Choose the actual
coordinator hostname and ingress from the cluster's existing DNS/TLS setup; example
hostnames below are not provisioned endpoints. Production and staging need separate
observation environments, secrets and explicit publication scopes.

Use the normal `frameworks cluster release plan` and `cluster release apply --dry-run`
with the updated manifest before applying the release. Release application initializes
the declared observer database, applies ClickHouse expand migrations and deploys the
observer and analytics/API services. Verify observer `/ready`, deploy the compatible
gateway fork through its managed-dependency lifecycle, and install the external probers.
Confirm real discovery in the inventory, real gateway observations in the public API,
and the dashboard's observer coverage before retiring the old scripts. Livepeer alerts
are disabled; new Ops/Business Pulse webhook destinations require no Livepeer rollout.

## External probers

Build with `make build-bin-network-prober`, or use the matching release's Linux amd64 or
arm64 `network-prober` binary after checking its release checksum. These hosts do not
need the FrameWorks stack, Node/PM2 or CLI enrollment. Configure a unique stable ID,
region, verified HTTPS coordinator URL, shared secret and persistent spool directory
using `api_network_observer/deploy/network-prober.env.example`.

The Linux release tarball includes `install-network-prober.sh`,
`network-prober.service` and `network-prober.env.example` alongside the binary. Extract
it on the prober host, rename the architecture-suffixed binary to `network-prober`
for the commands below, and copy the example to a private `network-prober.env`.
The installer and unit stay together in the extracted directory. A source checkout
uses the same files from `api_network_observer/deploy/`.
The supplied systemd unit grants writable state at `/var/lib/frameworks-network-prober`;
use that path for `NETWORK_PROBER_SPOOL_DIR` with this installer.

Put the Ethereum broadcaster address and discovery signature in a separate private
identity file:

```dotenv
LIVEPEER_BROADCASTER_ADDRESS=0x…
LIVEPEER_BROADCASTER_SIGNATURE=0x…
```

An existing valid pair works directly. In the legacy JavaScript configuration,
`CONF_BROADCASTER` maps to the address; `CONF_SIGNATURE` is the same 65 signature bytes,
encoded as hex rather than a JavaScript array. No private key belongs on the prober.
To create another pair, run the optional helper on the wallet host:

```bash
./network-prober sign-discovery --keystore wallet.json --password-file wallet-password --output network-prober.identity.env
```

The password file must have mode 0600 or stricter. The helper writes a new mode-0600
identity file and refuses to overwrite an existing file. Discovery signs the
checksummed address with go-livepeer's Ethereum hash/signature convention. This command
does not fund a wallet or send a transaction. The broadcaster may need sender reserve
for discovery admission even though the prober submits no paid transcodes.

On the Linux prober host, make the configuration and identity files private, validate
them offline, then install:

```bash
chmod 600 network-prober.env network-prober.identity.env
./network-prober check-config --env-file network-prober.env --identity-file network-prober.identity.env
sudo ./install-network-prober.sh --binary ./network-prober --config network-prober.env --identity network-prober.identity.env
```

Keep the installer beside its supplied service template. It creates the dedicated
service user and persistent state directory, installs the files and starts
`frameworks-network-prober.service`. Add `--no-start` to prepare a host without starting
it. On later reconfiguration, omitting `--identity` preserves the installed pair.
After replacing a running binary or configuration, restart the service explicitly with
`sudo systemctl restart frameworks-network-prober.service`.

Each process resolves the whole catalog every five minutes and executes only its
assigned endpoint discovery checks. It does not submit synthetic transcodes or require
broadcaster funding for synthetic work. Orchestrator self-signed discovery certificates
are accepted by default, matching Livepeer; the coordinator connection still verifies
TLS. Keep the spool directory persistent and exclusive to this process.

Local port 18025 exposes `/health` with spool counts, `successful_discovery_checks`,
`last_discovery_success` and `admission_rejections`. `/ready` checks recent coordinator
connectivity only. Verify a real successful discovery and its arrival in the inventory
before retiring an old prober. Authentication and sender-reserve failures are recorded
separately and do not count as worker downtime. Firewall that operational endpoint
appropriately for the host.
Observer heartbeat and DNS-cycle reports disclose queue depth and lost observations.
An unavailable prober does not make the orchestrator unavailable.

## Gateway

Configure a stable `FRAMEWORKS_GATEWAY_ID`, `FRAMEWORKS_GATEWAY_REGION`,
`FRAMEWORKS_CLUSTER_ID`, `FRAMEWORKS_CLUSTER_OWNER_TENANT_ID`,
`FRAMEWORKS_DECKLOG_GRPC_ADDR` and the existing service authentication/TLS settings.
Set `FRAMEWORKS_TELEMETRY_SPOOL_DIR` to persistent private storage when containerizing;
the default is under the gateway user's `.lpData/frameworks-telemetry` directory.
Set `FRAMEWORKS_NETWORK_ID=42161` and `FRAMEWORKS_ENVIRONMENT` to the coordinator namespace.

Per-orchestrator work totals require the gateway build with accounting version 1.
Apply the release's `002_network_work.sql` ClickHouse expand migration before upgrading
Periscope ingestion and queries. Existing gateway observations remain readable, but
their missing work and charge fields appear as unaccounted coverage. This extension
uses the same telemetry credentials and spool; probers do not require new settings.
The dashboard separates submitted work, accepted source minutes, reported pixels,
service charges and expected ticket credit. These describe FrameWorks gateway traffic,
not all work or redeemed earnings across the Livepeer network.

The optional `FRAMEWORKS_NETWORK_OBSERVER_URL` and
`FRAMEWORKS_NETWORK_OBSERVER_SECRET` enable candidate hints. Keep
`FRAMEWORKS_CANDIDATE_FEED_MODE=shadow` initially; `supplement` adds fresh hints without
replacing local discovery or relaxing local eligibility checks. HTTP overrides are for
isolated local development only.

## API filters

The public route accepts RFC3339 `start`/`end` (maximum 730-day window), `resource`
(onchain address), `ip`, `region`, `interval` (`1m`, `5m`, `1h`) and
`include_inactive=true`. Windows beyond raw retention use hourly snapshots and identify
that in the response. Prices and raw checks retain 30 days. Whole-window summaries and
bounded chart series are separate fields; inspect `truncated` before treating a series
as complete.

Livepeer notifications and incident escalation are disabled in this version. Operational
incidents and business pulse delivery can be routed separately using Lookout's purpose
settings in the configuration reference.
