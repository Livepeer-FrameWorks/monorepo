Browser-based broadcasting: cameras, screen share, media files, scenes and overlays, mixed in the browser. No encoder software needed.

<Aside type="caution" title="Beta: the SDK will change a lot">
  StreamCrafter is in beta, and its packages are on 0.x. Expect breaking changes in minor releases
  while cloud production and guests are built. Pin an exact version and read the package changelog
  before you upgrade.
</Aside>

<Aside type="tip" title="When to use StreamCrafter vs OBS">

Use StreamCrafter for browser-based streaming, screen shares, webcam broadcasts, and interactive apps. The drop-in studio switches scenes with cuts, fades and slides, puts logos and text over the picture, plays media files into the mix, and has a noise gate, de-esser, EQ and ducking for the audio.
Use OBS or a hardware encoder for long or high-stakes broadcasts, for filters and effects StreamCrafter does not have, or on a computer that cannot spare the CPU for a mix in the browser.

</Aside>

## Quick Start

### Direct WHIP mode

Pass the WHIP endpoint shown in the dashboard:

```tsx
<StreamCrafter whipUrl="%INGEST_URL%/webrtc/your-stream-key" initialProfile="broadcast" />
```

### Gateway resolution mode

The SDK resolves the WHIP endpoint from a stream key via `resolveIngestEndpoint`, which picks the ingest node closest to and least loaded for the publisher:

```tsx
import { StreamCrafter } from "@livepeer-frameworks/streamcrafter-react";
import "@livepeer-frameworks/streamcrafter-react/streamcrafter.css";

<StreamCrafter
  gatewayUrl="%GATEWAY_URL%/graphql"
  streamKey="<YOUR_STREAM_KEY>"
  initialProfile="broadcast"
/>;
```

<Aside type="note" title="Gateway vs Direct">
  There is **no default gateway**. Pass either `whipUrl` or (`gatewayUrl` + `streamKey`). If both
  are provided, `whipUrl` takes priority. The `gatewayUrl` path calls the public
  `resolveIngestEndpoint` GraphQL field. Call Gateway resolution from the publisher's browser so
  ingest routing uses the publisher's location; backend-side resolution routes from the backend's
  IP.
</Aside>

The drop-in component includes video preview, Add Camera, Share Screen and Add Media File, quality selection, the Go Live button, the source mixer, the producer controls, the audio section, a connection health indicator while live, and auto-reconnection.

## Producer Controls

While the compositor runs, the drop-in studio shows a producer panel under the preview. It is on by
default in every binding; turn it off with `showProducerPanel={false}` on React and Svelte, or
`show-producer-panel="false"` on the web component.

| Section  | What it does                                                                     |
| -------- | -------------------------------------------------------------------------------- |
| Scenes   | Create, delete and switch scenes with a cut, fade or slide of a chosen duration  |
| Layers   | Show, hide, reorder and remove the layers of the active scene, and set opacity   |
| Overlays | Add a logo image or text to the active scene, and set its position, size, colour |
| Media    | Play, pause and loop the media files added with Add Media File                   |

`]` and `[` switch to the next and previous scene while the studio has focus.

The Audio section appears while the studio captures. It sets the browser's echo cancellation,
noise suppression and auto gain for the microphones, and a noise gate, de-esser, three-band EQ and
ducking on the mixed audio. Ducking lowers every other source while the first camera's microphone
picks up sound.

## Where to Find Your WHIP URL

Your WHIP ingest URL is shown in the FrameWorks dashboard under **Ingest URLs**:

```
WHIP: %INGEST_URL%/webrtc/your-stream-key
```

FrameWorks uses MistServer's `/webrtc/{streamKey}` path for WHIP ingest. The dashboard URL points at
the `edge-ingest` DNS name, which resolves to the geographically nearest healthy ingest node.

## Ingest Front Door

The DNS name steers on geography alone. For load-aware routing without a GraphQL call, publish
against Foghorn's ingest front door instead:

```
POST https://foghorn.{base}/ingest/{streamKey}
```

It validates the stream key, scores candidate ingest nodes on load and distance, and answers with a
`307 Temporary Redirect` to the chosen node's WHIP URL.
[RFC 9725](https://www.rfc-editor.org/rfc/rfc9725.html#section-4.5) requires WHIP clients to support
redirects on the initial `POST`, and `307` preserves the method and SDP offer, so any spec-compliant
WHIP client can publish to this URL in place of a fixed node URL.

The same path answers `GET` with JSON when you need the candidates rather than a redirect — useful
for encoder setup scripts:

```bash
curl https://foghorn.{base}/ingest/{streamKey}
```

Require your encoder's protocol with `?protocol=whip`, `?protocol=rtmp`, or `?protocol=srt`:

```bash
curl 'https://foghorn.{base}/ingest/{streamKey}?protocol=srt'
```

This filters candidates before ranking and limiting the response. If no eligible node advertises
that protocol, the response is unavailable; it does not substitute a different protocol. Omit the
parameter to discover any advertised ingest protocols. WHIP `POST` always requires WHIP, and an
explicit conflicting protocol or duplicate protocol parameter returns `400`.

The URLs below illustrate one node's listeners, not fixed platform-wide ports. A node that does
not advertise a protocol omits its URL. Resolution is advisory, not a reservation or confirmation
that publishing has started.

Use the returned URL for the selected protocol unchanged. `baseUrl` identifies the node's public
HTTP(S) endpoint; its scheme and port are not the RTMP or SRT listener's scheme and port. Do not
reconstruct publishing URLs from it or assume every returned node supports every protocol.
Resolve with an explicit protocol when your encoder requires one.

```json
{
  "primary": {
    "nodeId": "edge-ams-1",
    "baseUrl": "https://edge-ams-1.{cluster}.{base}",
    "whipUrl": "https://edge-ams-1.{cluster}.{base}/webrtc/{streamKey}",
    "rtmpUrl": "rtmp://edge-ams-1.{cluster}.{base}:1935/live/{streamKey}",
    "srtUrl": "srt://edge-ams-1.{cluster}.{base}:8889?streamid={streamKey}",
    "region": "eu-west",
    "loadScore": 1950,
    "kind": "INGEST_ENDPOINT_KIND_NODE_SPECIFIC",
    "clusterId": "media-eu-1"
  },
  "fallbacks": [...]
}
```

RTMP and SRT have no redirect mechanism, so those protocols use either the `edge-ingest` DNS name or
a URL taken from this response. Resolution never claims ingest placement — the publish itself does —
so it is safe to call speculatively or repeatedly.

The Foghorn listener hostname does not constrain the result to one virtual media cluster. Commodore
supplies the stream's authorized healthy cluster envelope, and an existing live claim pins reconnects
to the cluster already receiving the publisher.

Errors use these statuses:

| Status | Cause                                                                                              |
| ------ | -------------------------------------------------------------------------------------------------- |
| `400`  | Missing stream key, invalid or duplicate `protocol` parameter, or a `POST` that is not WHIP        |
| `402`  | Negative account balance, or an ended trial or arranged plan (code `GRANT_EXPIRED`)                |
| `403`  | Account suspended or inactive, or the tenant is not entitled to the cluster or its class           |
| `404`  | Unknown stream key                                                                                 |
| `409`  | The stream's source mode does not accept push ingest, or the stream is already ingesting elsewhere |
| `415`  | The ingest protocol is not supported for this stream                                               |
| `429`  | Per-IP rate limit exceeded; the response carries `Retry-After`                                     |
| `503`  | Cluster unhealthy, no ingest-capable node available, or stream validation unavailable              |

<Aside type="caution" title="Stream Key is Secret">
  Your stream key grants permission to broadcast to your stream. Never share it publicly.
</Aside>

## Quality Profiles

The drop-in UI exposes three quality presets. The lower-level core type also accepts `auto` for
custom integrations that want browser-selected defaults:

| Profile        | Resolution | Use Case                    |
| -------------- | ---------- | --------------------------- |
| `professional` | 1920x1080  | High quality, good upload   |
| `broadcast`    | 1920x1080  | Balanced quality/bandwidth  |
| `conference`   | 1280x720   | Limited bandwidth, meetings |

```tsx
<StreamCrafter initialProfile="conference" />
```

## Multi-Source Streaming

StreamCrafter supports simultaneous camera + screen share with per-source volume control and audio mixing.

```tsx
const { startCamera, startScreenShare, sources } = useStreamCrafterV2({ ... });

await startCamera();
await startScreenShare({ audio: true });
// Both sources now stream together with mixed audio
```

See [Advanced Features](/builders/ingest-advanced/) for audio mixing details.

## Compositor

The compositor is **enabled by default** — multi-source layout control with scenes and layers:

- 17 layout presets (solo, PiP, split, grid, featured, and more)
- Layer ordering through `reorderLayers()` or the `LayerList` component in the producer panel
- Scenes from the producer panel or the compositor API, with cuts, fades, and slides between them
- Logo and text overlays, and media files as sources
- GPU-accelerated rendering (WebGPU, WebGL, Canvas2D fallback)

See [Compositor](/builders/ingest-compositor/) for full details.

## States

| State                    | Description                                                  |
| ------------------------ | ------------------------------------------------------------ |
| `idle`                   | Ready, no capture active                                     |
| `requesting_permissions` | Waiting for camera/mic permission                            |
| `capturing`              | Media captured, not streaming. A failed session returns here |
| `connecting`             | Establishing WHIP connection                                 |
| `streaming`              | Live and streaming                                           |
| `reconnecting`           | Connection lost, attempting reconnect                        |
| `error`                  | Error occurred                                               |
| `destroyed`              | Cleanup complete                                             |

## Browser Support

StreamCrafter publishes no minimum browser versions. What runs depends on the browser APIs below:

| Capability               | Browser APIs                                                                   |
| ------------------------ | ------------------------------------------------------------------------------ |
| Publishing               | `RTCPeerConnection`                                                            |
| Camera and microphone    | `getUserMedia`, which requires a secure context                                |
| Screen share             | `getDisplayMedia`                                                              |
| Compositor               | Web Workers and `OffscreenCanvas`; `enableCompositor()` rejects if setup fails |
| Background-safe encoding | WebCodecs and `RTCRtpScriptTransform`                                          |

<Aside type="note" title="Background Tab Behavior">
  Background-safe encoding requires WebCodecs **and** RTCRtpScriptTransform support
  (Chromium-family). Without that path, browser encoders may pause when the tab loses focus.
</Aside>

## Troubleshooting

### Camera/Microphone Not Working

- **Check permissions** — Ensure the browser has camera/mic access
- **HTTPS required** — MediaDevices API requires secure context
- **Device in use** — Close other apps using the camera

### Stream Won't Connect

- **Check WHIP URL** — Verify the endpoint is correct
- **Firewall/NAT** — WebRTC may need TURN servers for restrictive networks (pass `iceServers` in config)
- **Stream key** — Ensure the stream key is valid

### High Latency

- **Upload bandwidth** — Check your upload speed matches the profile bitrate
- **Profile mismatch** — Try `conference` profile for limited bandwidth

### Screen Share Audio Missing

- **System audio** — Screen share audio only works with `{ audio: true }`
- **Browser support** — System audio capture requires Chrome/Edge (not Firefox/Safari)
- **User selection** — User must check "Share audio" in the browser dialog
