FrameWorks supports wallet-based identity and on-chain payments alongside traditional email login and card / Mollie billing. This page covers the GraphQL surface; for the agent-facing flows see [agents/wallet-auth](/agents/wallet-auth) and [agents/payments](/agents/payments).

<Aside type="caution">
  Wallet operations and x402 payments authorize on-chain activity and balance movements. Treat them
  with the same care as billing actions — the API surface is small, but the side-effects are real
  money.
</Aside>

## Linking a wallet

A tenant can link one or more wallets. Linking requires a signed challenge from the wallet to prove ownership.

```graphql
mutation LinkWallet {
  linkWallet(input: { address: "0x...", signature: "0x...", message: "<challenge>" }) {
    __typename
    ... on WalletIdentity {
      id
      address
      createdAt
      lastAuthAt
    }
    ... on ValidationError {
      field
      message
    }
  }
}
```

To remove a wallet:

```graphql
mutation UnlinkWallet {
  unlinkWallet(walletId: "<wallet global id>") {
    __typename
    ... on DeleteSuccess {
      success
      deletedId
      pending
    }
    ... on NotFoundError {
      message
    }
    ... on AuthError {
      message
    }
  }
}
```

## Signing in with a wallet

`walletLogin` exchanges a signed challenge for a developer/session token. Use it to bootstrap a fresh tenant from an agent or wallet-only client.

First request the single-use message from `POST /auth/wallet-challenge` with
`{"address":"0x...","chain_id":1}`. Sign the returned `message` verbatim;
client-generated nonces and replayed challenges are rejected.

```graphql
mutation WalletLogin {
  walletLogin(input: { address: "0x...", signature: "0x...", message: "<challenge>" }) {
    __typename
    ... on WalletLoginPayload {
      token
      expiresAt
      isNewAccount
      user {
        id
        email
        role
      }
    }
    ... on ValidationError {
      field
      message
    }
  }
}
```

If the wallet isn't yet linked to a tenant, the mutation creates one. To bind an email address to an existing wallet-only tenant later, use `linkEmail`.

## x402 micropayments

x402 (HTTP 402 Payment Required) is an authenticated prepaid top-up protocol on FrameWorks. The platform issues a tenant-bound 402 response; the caller submits a signed payment proof; the server waits for confirmation, credits the balance, and reevaluates the original request. It is not a login method.

The user-facing entry point is `submitX402Payment`:

```graphql
mutation Pay {
  submitX402Payment(payment: "<base64 PAYMENT-SIGNATURE>", resource: "graphql://createStream") {
    __typename
    ... on X402PaymentResult {
      success
      tenantId
      walletAddress
      creditedCents
      newBalanceCents
      txHash
      message
    }
    ... on ValidationError {
      field
      message
    }
    ... on NotFoundError {
      message
    }
    ... on AuthError {
      message
    }
  }
}
```

Most clients won't call this directly — the SDK and MCP server handle it transparently. See [agents/payments](/agents/payments) for the full request/replay flow.

## Top-ups and balances

Wallet-funded crypto top-ups follow the standard prepaid-balance model. Initiate one via `createCryptoTopup`, then poll `cryptoTopupStatus` for confirmation count and the credited balance:
Complete the tenant billing address first; it supplies the customer country used
for the top-up VAT decision and invoice.

```graphql
mutation Topup {
  createCryptoTopup(input: { amountCents: 10000, asset: USDC, currency: "EUR" }) {
    topupId
    depositAddress
    asset
    expectedAmountBaseUnits
    expectedAmountToken
    quotedPriceUsd
    quoteSource
    quotedAt
    expiresAt
    network
  }
}

mutation CheckStatus {
  cryptoTopupStatus(topupId: "<topup id>") {
    id
    status
    txHash
    confirmations
    receivedAmountBaseUnits
    receivedAmountToken
    creditedAmountCents
    creditedAmountCurrency
  }
}
```

Once credited, the funds appear in your prepaid balance (`prepaidBalance` query) and are spent against usage like any other top-up.
The confirmed credit is the VAT tax point and creates the retained top-up invoice;
later usage only consumes that already-invoiced balance.
