Configure your encoder for FrameWorks. Covers OBS Studio, FFmpeg, RTMP/E-RTMP, SRT, WHIP, and HTTP Matroska (MKV).

<Aside type="note" title="Works everywhere">
  These encoder settings are the same for managed and self‑hosted deployments. Ingest endpoints and
  exposed ports can differ, so use the URLs shown in your dashboard.
</Aside>

## OBS Studio

OBS is free and works on Windows, Mac, and Linux. [Download it here](https://obsproject.com/).

### Stream Settings

1. In OBS Studio, navigate to **Settings**, then select the **Stream** tab.
2. Configure the following:
   - **Service:** Custom
   - **Server:** `%RTMP_URL%`
   - **Stream Key:** From your stream's **Stream Key** card in the dashboard

FrameWorks accepts Enhanced RTMP (E-RTMP) on the same ingest endpoint. If your encoder exposes
Enhanced RTMP options for newer codecs, keep the same server URL and stream key.

### Recommended Output Settings

Use these values as a starting point, then reduce bitrate or resolution if the encoder cannot maintain them or the uplink lacks headroom.

Go to **Settings → Output** and select **Advanced** mode.

**Streaming tab:**
| Setting | Value |
|---------|-------|
| Encoder | NVIDIA NVENC (if available) or x264 |
| Rate Control | CBR |
| Bitrate | 4500 kbps (for 1080p30) |
| Keyframe Interval | 2 seconds |
| Preset | Quality (GPU) or veryfast (CPU) |
| Profile | high |

**Video tab:**
Set the output resolution and frame rate here:
| Setting | Value |
|---------|-------|
| Base Resolution | Your monitor resolution |
| Output Resolution | 1920x1080 |
| Downscale Filter | Lanczos |
| FPS | 30 or 60 |

### Audio Settings

Use these audio settings for broad playback compatibility:

**Settings → Audio:**

- **Sample Rate:** `48 kHz`
- **Channels:** `Stereo`

**Settings → Output → Audio:**

- **Audio Bitrate:** `160 kbps` (per track, suitable for most streams) or `320 kbps` (for high-fidelity audio, especially music)

## FFmpeg

FFmpeg works well for scripted or headless publishing. These commands send RTMP to FrameWorks:

```bash
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 4500k -maxrate 4500k -bufsize 9000k \
  -g 60 -keyint_min 60 \
  -c:a aac -b:a 160k -ar 48000 \
  -f flv "%RTMP_URL%/{stream-key}"
```

From a webcam:

```bash
ffmpeg -f v4l2 -i /dev/video0 -f alsa -i default \
  -c:v libx264 -preset ultrafast -b:v 2500k \
  -c:a aac -b:a 128k \
  -f flv "%RTMP_URL%/{stream-key}"
```

## SRT (Alternative Protocol)

SRT (Secure Reliable Transport) offers improved performance over RTMP, especially on unstable or high-latency networks, by ensuring secure and reliable stream delivery. Use this URL format:

```
srt://%INGEST_HOSTNAME%:%SRT_PORT%?streamid={stream-key}&latency=200&mode=caller
```

In OBS: **Settings → Stream → Service → Custom**, then paste the SRT URL in Server.

If you’re self‑hosting, make sure the SRT port is exposed on your ingest endpoint (default is `%SRT_PORT%`).

**FFmpeg with SRT:**

```bash
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 4500k \
  -c:a aac -b:a 160k \
  -f mpegts "srt://%INGEST_HOSTNAME%:%SRT_PORT%?streamid={stream-key}&latency=200&mode=caller"
```

## WHIP (WebRTC)

WHIP (WebRTC-HTTP Ingestion Protocol) provides a modern approach for browser-based ingestion, enabling real-time streaming with sub-second latency directly from your web browser or compatible software. The dashboard shows your specific WHIP URL on the stream details page.

```
%INGEST_URL%/webrtc/{stream-key}
```

If you’re self‑hosting behind a proxy, make sure the WHIP path is reachable on your ingest endpoint.

### Load-aware WHIP URL

`%INGEST_URL%` is a geo-DNS name: it resolves to the nearest healthy ingest node, but does not
account for how loaded that node is. Foghorn's ingest front door adds load awareness to WHIP:

```
%PLAY_URL%/ingest/{stream-key}
```

Publishing a WHIP `POST` there returns a `307 Temporary Redirect` to the selected node's WHIP URL.
[RFC 9725](https://www.rfc-editor.org/rfc/rfc9725.html#section-4.5) requires WHIP clients to support
redirects on the initial `POST`, and `307` preserves the method and SDP offer, so any spec-compliant
WHIP client can use this URL in place of a fixed node URL.

The same path answers `GET` with JSON, which is useful in setup scripts that need a concrete node
URL for a protocol that cannot follow redirects:

```bash
curl %PLAY_URL%/ingest/{stream-key}
```

RTMP, SRT and HTTP MKV pushes do not follow this redirect, so those protocols use either the geo-DNS
`%INGEST_HOSTNAME%` name above or the `rtmpUrl` / `srtUrl` / `mkvUrl` from that JSON response.

## HTTP Matroska (MKV)

A tool that writes Matroska or WebM can publish over plain HTTP by streaming the file body to the
stream key's `.mkv` path with a chunked `PUT` or `POST`:

```
%INGEST_URL%/{stream-key}.mkv
```

**FFmpeg piped into curl:**

```bash
ffmpeg -re -i input.mp4 \
  -c:v libx264 -preset veryfast -b:v 4500k -g 60 \
  -c:a aac -b:a 160k \
  -f matroska -live 1 - |
  curl -sS --fail -H 'Content-Type: video/x-matroska' -T - "%INGEST_URL%/{stream-key}.mkv"
```

The request stays open for as long as the stream is live; closing it ends the session. Matroska
keeps track metadata such as a rotation flag. A self-hosted proxy in front of the edge must stream
request bodies to MistServer instead of buffering them.

For a specific edge that runs MistServer's Matroska output, ask the front door with
`?protocol=mkv` and use the `mkvUrl` from the JSON response:

```bash
curl '%PLAY_URL%/ingest/{stream-key}?protocol=mkv'
```

## Choosing the Right Bitrate

Higher bitrates can preserve more detail, but only when the encoder and uplink can sustain them. Use these ranges as a starting point:

| Resolution | FPS | Bitrate Range     |
| ---------- | --- | ----------------- |
| 720p       | 30  | 2,500–4,000 kbps  |
| 720p       | 60  | 3,500–6,000 kbps  |
| 1080p      | 30  | 3,500–6,000 kbps  |
| 1080p      | 60  | 4,500–8,000 kbps  |
| 1440p      | 30  | 5,000–15,000 kbps |
| 1440p      | 60  | 6,000–24,000 kbps |

These ranges are FrameWorks recommendations; adjust based on content complexity and network stability.

**Rule of thumb:** Your upload speed should be at least 2x your stream bitrate.

Run a speed test to [speedtest.net](https://speedtest.net) and check your upload.

## Selecting an Encoder

Hardware encoders reduce CPU use and are usually the best first choice when one is available.

- **NVIDIA NVENC:** Offers the best quality-to-performance ratio. Highly recommended if you have an NVIDIA GPU.
- **AMD AMF:** A solid choice for users with AMD graphics cards.
- **Intel QuickSync:** efficient and widely available on most Intel CPUs with integrated graphics.
- **x264:** Software-based encoding. It ensures compatibility everywhere but consumes significant CPU resources. Use this only if hardware encoding isn't an option.

In OBS Studio, you can select your encoder under **Settings → Output → Encoder**.

## Adaptive Bitrate (ABR)

FrameWorks generates lower-quality renditions of your stream so viewers on slower connections can watch without buffering. The default live-stream process configuration uses Livepeer Gateway for video ABR and local AV processes for audio compatibility.

### How It Works

When you go live, the control plane attaches your tier's live process configuration to the stream.
Every tier defaults to the **standard** ladder for live streams and VOD processing. Paid tiers also allow **qhd** and **uhd**:

| Rendition       | Bitrate     | Added when the source's short side is at least |
| --------------- | ----------- | ---------------------------------------------- |
| 360p            | 900 kbps    | 360 px                                         |
| 480p            | 1600 kbps   | 480 px                                         |
| 720p            | 4500 kbps   | 720 px                                         |
| 1080p           | 7800 kbps   | 1080 px                                        |
| 1440p (qhd/uhd) | 10,800 kbps | 1440 px                                        |
| 2160p (uhd)     | 15,000 kbps | 2160 px                                        |

The short side is the height of a landscape source and the width of a portrait one. When the
source has several video tracks, the one with the highest bitrate is the source. Sources whose
short side is below 360 px get no video renditions. Renditions keep the source frame rate and use
`H264ConstrainedHigh`. Audio compatibility processes generate Opus when the incoming audio is not
already Opus and AAC when it is not already AAC.

### Original tracks used as renditions

When a video track you send already matches a rendition, FrameWorks serves that track as the
rendition instead of encoding it again. This covers the source itself and every extra video track
of a multitrack publish (E-RTMP multitrack, HTTP Matroska) or a multi-rendition upload. A track
fills a rendition when all of these hold:

- it is H264, upright and not mirrored;
- its short side is within 32 px of the rendition's, or 5% for 720p and above;
- its bitrate is between half and twice the rendition's bitrate;
- for live streams, it has no B-frames (set your encoder's B-frames to 0, or use the `baseline`
  profile).

| Rendition | Short side kept | Bitrate kept      |
| --------- | --------------- | ----------------- |
| 360p      | 328–392 px      | 450–1,800 kbps    |
| 480p      | 448–512 px      | 800–3,200 kbps    |
| 720p      | 684–756 px      | 2,250–9,000 kbps  |
| 1080p     | 1026–1134 px    | 3,900–15,600 kbps |
| 1440p     | 1368–1512 px    | 5,400–21,600 kbps |
| 2160p     | 2052–2268 px    | 7,500–30,000 kbps |

When two tracks qualify, the one whose bitrate is closest to the rendition's bitrate is used. A
rendition filled by your own track is not transcoded and not billed as processing. The decision is
made once, when the tracks arrive: FrameWorks waits up to 5 seconds for each track to report its
size and bitrate, and a track that has not reported them by then is encoded instead. Changing the
bitrate later does not switch a rendition between kept and encoded; reconnecting does.

HEVC, rotated and mirrored tracks are still used as the source for encoding, but they never fill
an H264 rendition themselves.

Set a stream's advanced `liveVideoAbr` option to `OFF` to omit its live video
renditions on the next ingest session. Audio compatibility and thumbnail
processes continue. A destination that needs a lower or different video track
may have no compatible track when live video ABR is off.

Foghorn fills in the Livepeer Gateway instances for the stream's cluster at dispatch time. If no
Livepeer Gateway is registered, each rendition is converted to a local MistProcAV process so the
media node encodes the same ladder itself.

### What This Means for You

- **Stream at the highest quality your upload supports.** The default ladder adds lower
  renditions up to the chosen ladder’s ceiling when the source is large enough.
- **Send renditions yourself if you already encode them.** An E-RTMP multitrack or Matroska
  publish whose tracks sit inside the ranges above is served as is, without a second encode.
- **Viewers automatically get the best available quality their connection supports** via HLS ABR,
  with DASH and LL-HLS available alongside on every cluster.

### Custom Transcoding Profiles

Choose a named ladder in stream create/edit settings, under **Streams → Default transcode ladder**,
or for an individual library upload. Resolution follows the stream or upload choice, then the account
choice, then the plan default. `transcodeLadderPolicy` lists the allowed ladders; use
`setTranscodeLadderPolicy(input: { ladder: "uhd" })` to set the account default. Empty means inherit.
A stream's choice applies on its next broadcast. A plan downgrade preserves a stored choice but
uses the next allowed default until the account upgrades again. Custom process overrides remain
independent of these named ladders. Live video ABR `OFF` still suppresses video renditions.

Once at least one rendition is encoded, every original video track that fills no rendition, the
source included, is hidden from playback and from the saved recording, so an off-ladder or
out-of-range track cannot sit next to the encoded rendition that replaces it. Tracks that fill a
rendition stay visible as that rendition. A source below every rendition keeps playing as is.
Keep the [original upload](/builders/recordings#original-uploads) when source quality is needed.
Named ladders preserve frame rate; they do not add a separate 60 fps profile.

## Avoid Common Pitfalls

**Leave upload headroom**
If you experience dropped frames or instability, your bitrate might be too high for your internet connection. Try lowering it to stabilize the stream.

**Stick to a 2-Second Keyframe Interval**
Always set your keyframe interval to `2` seconds. Longer intervals can cause playback buffering or failures for viewers joining mid-stream.

**Verify Your Audio Source**
Silence is a common issue. Double-check that your microphone or desktop audio is selected and unmuted in the OBS audio mixer.

**Use Constant Bitrate (CBR)**
Variable Bitrate (VBR) is excellent for recording but problematic for live streaming due to fluctuating bandwidth usage. Always use **CBR** for a consistent stream.
